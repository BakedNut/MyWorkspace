# 백엔드 운영

200번 Rocky Linux 9 LXC에서 Nginx·Java 21·Spring Boot를, 202번에서 MySQL 8.4.13을 실행한다. 201번 NPM이 HTTPS를 종료하고 200번 Nginx가 정적 화면과 `/api`를 제공한다. 백엔드는 전용 사용자 `myworkspace`로 127.0.0.1:8080에서만 실행한다.

## 인증과 비밀정보

- 초기 비밀번호는 200번 `/etc/myworkspace/login-password`에 root만 읽을 수 있게 저장했다. 채팅·Git·프론트엔드에 포함하지 않는다. `/etc/myworkspace/application.env`에는 BCrypt 해시와 DB·Proxmox 연동 설정이 있다. 이 파일도 root 전용이다.
- `TRUSTED_NETWORKS`에 지정한 집 내부망은 요청마다 자동 입장을 판정한다. 현재 값은 `192.168.1.0/24`다. Tailscale 서브넷 연결은 Proxmox의 SNAT를 거쳐 같은 LAN 주소로 도달한다. 학교 IP를 향후 방화벽에서 허용하더라도 이 목록에 추가하지 않으면 비밀번호 로그인을 요구한다.
- Nginx는 201번 NPM의 `X-Real-IP`만 신뢰하고 앱에 전달할 IP·프로토콜 헤더를 덮어쓴다. Tomcat은 루프백 프록시만 신뢰한다. 임의의 전달 IP 헤더로 자동 입장할 수 없다. Nginx의 접속 허용 목록은 실제 전송 경로에 적용한다.
- 비밀번호 세션은 HttpOnly·SameSite=Lax이며 HTTPS에서는 Secure도 적용된다. 로그인 시 세션 ID를 바꾸고 로그아웃 시 폐기한다. 기본 만료는 12시간이며 로그인 시도는 IP별 15분에 5회로 제한한다. 앱 재시작은 기존 비밀번호 세션을 만료시킨다.
- 내부망 자동 인증을 비밀번호 세션으로 저장하지 않는다. 외부 요청은 매번 다시 인증 대상이 된다. 일정·MAC 수정·WOL 전송을 포함한 모든 쓰기 요청은 CSRF 토큰을 검증한다.
- MySQL은 200번만 3306으로 접속할 수 있다. 런타임 DML 계정과 스키마 마이그레이션 계정을 분리했다. TLS로 통신하며 서버 CA를 검증한다. Proxmox HTTPS도 전용 CA를 검증한다.

## 일정과 이전 데이터

일정·시간표·WOL 목록은 MySQL에 저장한다. iCloud는 사용자 요청에 따라 나중에 연결한다. 현재 `내 일정`은 이 서버에 저장되는 일정이며 브라우저 전용 저장 기능이 아니다. iCloud 설정에 미연결 상태를 표시한다. 양방향 동기화·반복 일정의 iCloud 편집은 아직 지원하지 않는다.

공휴일은 Nager.Date의 한국 `Public` 피드를 사용한다. 현재 연도 전후 자료를 매일 갱신하고 다른 연도 조회 시에도 가져온다. 가져온 피드는 DB에 보관해 장애 시 유지하며, 캘린더에서 조회·갱신 문제를 표시한다. 공급처의 누락이나 변경 가능성은 있으므로 법정 일정 확인이 필요한 용도에서는 공식 발표와 대조한다.

기존 시안의 브라우저 저장 자료는 삭제하지 않았다. 해당 자료가 있는 브라우저에는 메뉴 아래 `기존 데이터 가져오기`가 표시된다. 일정·시간표·PC 목록을 확인하고 선택해서 한 번 가져올 수 있다. 서버 자료를 덮어쓰지 않고 오류 시 전체 변경을 취소한다. 예시 일정을 실제 자료로 가져오지 않도록 제목·수업·PC 목록을 확인한다.

## 실제 모니터링과 WOL

- Proxmox는 `myworkspace-monitor@pve!dashboard`의 읽기 전용 PVEAuditor 권한을 사용한다. 화면에서 VM/LXC 제어는 제공하지 않는다.
- 호스트·게스트 상태는 약 5초마다 수집하고 화면은 60초마다 갱신한다. 네트워크는 실제 누적 카운터의 차이를 초당 속도로 환산한다. 호스트 네트워크는 물리 인터페이스 합계다.
- CPU 온도는 비특권 `myworkspace-sensors` 계정의 고정 SSH 명령으로 수집한다. 키는 200번에서만 사용할 수 있으며 임의 명령·터널·대화형 셸을 허용하지 않는다.
- 기록은 MySQL에 저장한다. 최근 1시간은 5초 수준, 이후에는 분당 한 샘플을 최대 31일 유지한다. 조회 그래프는 `1m=5초`, `15m=1분`, `1D=15분`, `1W=1시간`, `1M=6시간`으로 평균 집계한다. 배포 전 과거 기록을 생성하지 않는다.
- LXC 파일시스템 사용량은 실제 값을 사용한다. QEMU VM은 게스트 파일시스템 정보를 얻지 못한 경우 사용량을 `null`로 표시한다. 호스트 스토리지 온도도 지원되지 않으면 미지원으로 표시한다.
- WOL은 저장된 MAC에만 매직 패킷을 전송한다. 목록은 최대 50개이며 잘못된·중복 MAC을 거부한다. 10초 요청 제한의 기준 시각은 DB에 저장한다. MAC만으로 실제 부팅을 확인할 수 없어 전송 성공과 부팅 미확인을 구분한다.
- 200·202번을 동일 LAN의 `/24`로 맞추고 201번에는 200번으로 향하는 직접 경로만 추가했다. 기존 설정은 호스트의 비공개 네트워크 백업 폴더에 보관했다. WOL 브로드캐스트는 `192.168.1.255:9`를 사용한다.

## 빌드·배포·복구

개발 환경에서 `BE/./mvnw verify`와 FE의 타입 검사·테스트·린트·빌드를 실행한다. Proxmox 호스트에서 `python3 BE/deploy/deploy.py`로 빌드된 파일을 배포한다. 이 스크립트는 root와 `pct` 접근 권한이 필요하다. 새 백엔드의 상태를 확인한 후 Nginx 설정과 정적 화면을 전환한다. 이전 JAR와 화면 디렉터리는 유지한다.

`BE/deploy/initialize.py`는 빈 MySQL 서버에만 사용하는 최초 설치용이다. 기존 데이터가 있으면 중단하며 재배포에서 실행하지 않는다. `monitoring.py`는 읽기 전용 계정·인증서를 설정한다. 설치 스크립트는 Proxmox에 포함된 도구와 호스트의 Python bcrypt를 사용한다. 비밀번호·토큰을 명령행에 넣지 않는다.

상태 확인은 200번의 `systemctl status myworkspace nginx`, 202번의 `systemctl status mysqld firewalld`를 사용한다. 앱 로그는 200번 `journalctl -u myworkspace`다. JVM 힙 상한은 384MB, 서비스 메모리 제한은 700MB다. MySQL 버퍼 풀은 128MB이며 연결은 최대 20개다.

이전 배포로 복구할 때는 200번 `/opt/myworkspace/releases/`의 이전 JAR와 `/var/www/myworkspace/releases/`의 대응 화면을 확인한 후 각 `current.jar`·`current` 링크를 전환하고 앱을 재시작한다. 스키마는 Flyway가 관리하므로 이전 코드의 스키마 호환성도 확인한다. 설정 파일을 복구할 때는 비공개 설정을 보존한다.

## 백업

호스트의 `myworkspace-backup.timer`가 매일 04:30 전후에 일관된 DB 덤프를 생성한다. 컨테이너 바깥의 `/root/.local/state/myworkspace/backups/`에 root 전용으로 최근 14개를 보관한다. 운영 비밀정보는 별도 root 전용 파일이므로 DB 백업에 포함되지 않으며 서버 전체 복구 시 안전한 별도 사본이 필요하다.

`python3 BE/deploy/backup.py --verify`는 백업 후 무작위 이름의 임시 DB에 복원해 테이블·마이그레이션 상태를 확인하고 임시 DB를 제거한다. 운영 DB를 덮어쓰지 않는다. 실제 재해 복구 시 앱을 중지하고 확인한 백업을 MySQL에 복원한 뒤 앱을 시작한다. 호스트 디스크 자체의 장애에 대비한 외부 백업 저장소는 아직 설정하지 않았다.

## 검증 기록

- 백엔드 통합 테스트 9개를 통과했다. 네트워크 자동 입장의 매 요청 판정·전달 IP 위조 거부·실제 CSRF 로그인·세션 갱신·로그아웃·로그인 시도 제한·DB 저장·시간표 충돌·WOL 서버 MAC 사용/쿨다운·기록 보관/누락 구간·이전 자료 가져오기를 포함한다.
- FE 테스트 44개, 타입·빌드·린트 오류 0건이다. 기존 Fast Refresh 경고 2개가 남아 있다. 운영 번들에는 예시 일정·데모 비밀번호·시안 상태 선택기가 포함되지 않는 것도 확인했다.
- Playwright Chromium에서 내부망 자동 입장, 실제 외부 HTTPS 로그인·새로고침·로그아웃, Secure·HttpOnly·SameSite=Lax 쿠키, 일정 모달 저장·재조회, 실제 금요일 공휴일 표시, Proxmox 상태와 5개 기간 API를 확인했다. 1440px PC와 320·390px 모바일에서 입력·메뉴·가로 넘침을 확인했고 최종 실행의 페이지 오류는 없었다. Safari 실기기는 미검증이다.
- 실제 LAN 브리지에서 102바이트 WOL 매직 패킷을 캡처하고 등록 MAC 일치·10초 재요청 거부·부팅 미확인을 확인했다. 임시 테스트 대상만 사용했고 실제 두 PC의 부팅은 아직 검증하지 않았다. 두 PC의 MAC은 WOL 목록 수정에서 입력한다.
- 실제 외부 경로에서 사용자 IP 헤더를 조작해도 401을 반환했다. 신뢰 프록시에서 IP가 누락되거나 잘못된 경우에도 로그인을 요구했다.
- 일정·시간표·PC 목록을 임시 저장한 후 앱을 재시작해 모두 유지되는 것을 확인하고 검증 항목만 삭제했다. 별도 임시 DB로 백업을 복원해 테이블·마이그레이션 무결성을 확인했다.
- 초기 MySQL의 엄격한 GROUP BY 오류와 빈 값 직렬화·WOL 부팅 상태 응답 차이를 실제 연동 검증 중 수정했다. 호스트와 게스트의 기록 키도 화면 계약에 맞춰 확인했다.
- 200·202번 `/24`와 201→200 직접 경로 적용 후 실제 내부망·HTTPS 경로를 재검증했다. Tailscale 맥북의 실제 재접속은 이번 변경 후 별도로 재현하지 않았다. 기존의 사용자 접속 복구 확인은 유지한다.
- 최종 기능 배포: `backend-18f94b610137-20261106T080101Z`. 앱·정적 파일의 이전 릴리스는 복구용으로 보존했다. iCloud 계정, VM 게스트 파일시스템 센서, 실제 PC 부팅 확인과 호스트 밖 백업 저장소는 아직 연결하지 않았다.
